# Cavaco Outreach Gmail adapter

Implemented `gmail_adapter.GmailAdapter`, with mocked HTTP contract tests and real
PostgreSQL worker integration tests. No live email has been sent or mailbox connected.

## Scope and wiring

Instantiate with an explicit database `mailbox_id`, the primary mailbox `email`, and
an injected `token_provider(timeout_seconds=...) -> access_token`. Pass the adapter
as `gmail` to `DeliveryWorker`. Never call `send` directly from the review handler.
The adapter has no database dependency and performs no database writes.

The credential provider must supply a valid OAuth access token within the provided
budget. Local browser consent, token refresh and private-file credential storage are now
implemented in `gmail_auth.py`; see GMAIL_AUTH.md. Cloud OAuth client creation and
live account onboarding still require the account owner. Do not paste tokens
into chat or commit credentials. No service-account delegation choice is implied.
A future OAuth provider should request gmail.send plus gmail.readonly for this
send-and-reconcile scope; metadata-only access cannot fetch raw message bodies.

Every operation verifies `/users/me/profile` against the pinned primary mailbox.
Send-as aliases are intentionally unsupported until explicitly validated. Requests
use only `https://gmail.googleapis.com`, TLS validation, no environment proxies,
no redirects, and an HTTP transport with retries disabled. The optional transport
argument is for trusted test injection only. There is no automatic retry after 401.

## Pinned payload and outcomes

The current pilot supports one plain-text recipient, with no attachments, CC, BCC,
or multipart MIME. It validates the approved sender, recipient, subject, body and
Message-ID against the stored base64url MIME; sends the original `raw_mime` string
unchanged; and includes threadId only when supplied. Reply headers must already
be present. The upstream preparation workflow must preserve the original subject
for Gmail threading. No Message-ID is generated by the adapter.

- HTTP 200 with valid message/thread identifiers: ACCEPTED.
- Explicit 400/401/403/404/413/422/429: REJECTED, with no safe-to-retry flag.
- Other responses, redirects, malformed success, send timeout or transport failure:
  UNCERTAIN. No second POST is attempted.
- Local validation, token acquisition, or profile failure before the send request:
  REJECTED (the worker stops this intent for operator investigation).

No raw exception/API error content is emitted or persisted. Status classification
is deliberately conservative. Confirm actual provider behavior in controlled tests
before live use. API acceptance does not prove recipient inbox delivery.

## Reconciliation

Search the authenticated mailbox using `rfc822msgid`, requiring the SENT label and
including spam/trash. Paginate up to ten pages of 100 candidates. Fetch raw MIME for
each distinct result, require sent status, and compare Message-ID, sender, recipient,
subject, reply headers, decoded text body, and expected thread. Line endings are
normalized for comparison only; the submitted payload is never reserialized.
Multiple matches, changed bodies, identity conflicts, malformed responses, API
errors, or exhausted pagination yield LOOKUP_FAILED. Zero results yields
NOT_FOUND_YET. Both remain reconciliation-only; neither permits a resend.
Provider-added multipart content or rewritten headers can conservatively remain
unresolved. Controlled mailbox testing must establish normal round-trip behavior.

A single monotonic budget is shared across token acquisition, profile, pages, and
message fetches. Each HTTP call gets the remaining timeout. HTTPX enforces socket
phase timeouts, not a hard process-wide wall-clock kill; a slow streaming response
or misbehaving credential provider can exceed the budget. The durable worker's
lease fencing still rejects stale completion, and replacement workers only
reconcile expired work. Deployment-level process supervision remains required.

Tests use httpx.MockTransport and synthetic credentials; no real Gmail request occurs.
They cover unchanged MIME, account mismatch, header injection, explicit rejections,
ambiguous errors/timeouts, missing IDs, pagination, conflicting/multiple matches,
